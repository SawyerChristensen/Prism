  **Done 7/25**:
  - **GPU buffer reuse.** Every waveform/shape/custom-waveform draw call was allocating a *brand-new* `MTLBuffer` via `device.makeBuffer(bytes:...)` every single frame (5-20+ allocations/frame for a preset with several shapes/custom waveforms) — same for the per-pixel warp mesh's vertex buffer (825 vertices, rebuilt fresh every frame for any preset with `per_pixel_N=`/`warp_N=`, a combined 80%+ of the corpus). projectM's own `Renderer/VertexBuffer.cpp` never does this: a `Mesh`'s buffers are created once and just updated in place every frame (`glBufferSubData` when the vertex count hasn't changed, `glBufferData` — an actual reallocation — only when it has, per `VertexBuffer<VT>::Update()`). Ported the same idea as a new `TransientBufferPool` in MilkdropMetalRenderer.swift: grow-only-when-needed buffers, updated via a direct `.contents()` memcpy (cheaper than even `glBufferSubData`, since `.storageModeShared` memory is already CPU-writable) instead of a fresh allocation. Triple-buffered (3 rotating generations keyed on `frameCounter % 3`, not just one reused buffer) since a `.storageModeShared` `MTLBuffer` has no automatic protection against the CPU overwriting a buffer the GPU hasn't finished reading yet from an earlier frame — the standard hazard-avoidance pattern for exactly this. Verified via a standalone `swiftc` harness (real `MTLDevice`, no app/CoreAudio involved) — 9 checks: distinct buffers within one frame never alias each other's data, the same generation bucket reuses (not leaks) its buffer across frames, a different generation bucket never aliases, and growing a slot to a larger size preserves full correctness, not just the first few bytes.

## Testing policy (added 7/25, after the CRLF parsing bug)

The CRLF bug (below) existed because every test — including ones explicitly labeled as covering
"real preset corpus" content — built its input from a Swift `"""` triple-quoted string literal,
even when the literal's *text* was transcribed from a real file. A `"""` literal always normalizes
line endings to plain `\n` regardless of the source file's own line endings, so it can never
reproduce a real file's actual on-disk bytes. That's a structural blind spot, not a one-off
mistake, so going forward:

- **Any feature that parses a new kind of preset input** (a new key family, a new encoding/format
  assumption, a new code path through an existing parser) **must be tested against at least one
  real, byte-for-byte-copied `.milk` fixture** — not a synthetic string literal, even a
  "verbatim-transcribed" one. Add it under `PrismTests/Fixtures/` (see `RealPresetFixtureTests.swift`
  for the pattern: `Bundle(for:)` + `url(forResource:withExtension:)`, resources auto-copy into the
  test bundle via the project's synchronized groups — confirmed working 7/25).
- **Before marking a parsing feature done, measure it against a real sample of the corpus** — not
  just "the unit test passes." The reference method (used for the CRLF fix and the per-pixel mesh
  work): a standalone `swiftc`-compiled harness (no Xcode project needed, since the parser files
  have no framework dependencies) that reads real files from the preset pack and reports actual
  counts — files parsed vs. failed, % with the new field/program non-empty, any exceptions. Report
  the real numbers in the TODO item, the way the CRLF fix and per-pixel mesh items below do — a
  feature that "looks right" against one or two files can still be silently wrong or silently inert
  against the other 9,793.
- Each Phase 1/2 item below that adds a new input format has this noted explicitly as **"needs:
  real-fixture test + measured corpus pass-rate"** — treat that as part of the feature, not a
  follow-up.
- **Preset library decision (7/25)**: Prism points at an external, user-chosen folder rather than
  bundling any preset pack into the app/repo — the full 9,795-preset pack is 259MB (vs. a 2.9MB
  `.git` today) and its redistribution rights are unclear (an aggregated community collection, no
  explicit license seen). `PrismTests/Fixtures/` is the one exception: 2 real files (~30KB total),
  used only for parser regression testing, not shipped as app content.

- [x] **Critical bug, fixed 7/25: the preset parser never actually parsed a single real preset.**
  `MilkdropPresetFile.init(text:)` split lines on the Character `"\n"`, but Swift's `String`
  treats `"\r\n"` as one Character (an extended grapheme cluster — `"\r\n".count == 1`), so that
  split found zero line breaks in a CRLF file and the whole file collapsed into one unparseable
  blob. Every `.milk` file sampled from the real preset pack (Windows-authored, as the whole
  Milkdrop/NestDrop ecosystem is) is CRLF — confirmed 800/800 in a random sample — so this wasn't
  an edge case, it silently defeated 100% of real-world presets: `nWaveMode`, `per_frame_N=`,
  shapes, everything stayed at struct defaults no matter what file got loaded. This is why loading
  different presets looked like nothing was happening. Every existing unit test used a `"""`
  triple-quoted Swift string literal, which always normalizes to plain `"\n"` regardless of the
  source file's own line endings — so nothing in the test suite ever exercised the CRLF path
  either. Fixed by splitting on `\.isNewline` instead (handles CRLF, lone LF, and lone CR alike);
  added `crlfLineEndingsParseCorrectly` to MilkdropPresetFileTests to catch a regression. Verified
  against a random 1,500-file sample of the real pack post-fix: 1500/1500 parsed with no
  exceptions, 98.6% have non-empty `per_frame_N=`, 60.7% have `per_pixel_N=` code, ~82% have
  `warp_N=`/`comp_N=` shader code.

  - **Key insight that made this tractable without a from-scratch rewrite**: `MilkdropMetalRenderer` already *was*, in isolation, exactly "render one preset's whole pipeline into a texture" — its `draw(in:)` only touched `view.currentDrawable` at the very top (a guard) and the very bottom (the final present pass); everything in between (feedback/warp mesh, shapes, waveforms, border/darken-center, `comp_N=`/old-style composite) already wrote into an internal `destTexture`. Renamed to `renderToTexture(view:) -> MTLTexture?`, dropped the drawable guard and the final present pass (now returns the finished texture instead) — **zero changes to the ~700 lines in between**, so the existing single-preset render path carries zero regression risk from this change.
  - **New `MilkdropMetalCoordinator.swift`**: `MilkdropMetalCoordinator` (new file) replaces `MilkdropMetalRenderer` as the actual `MTKViewDelegate` installed on the view, holding `activeRenderer` (always) + `outgoingRenderer` (only during a transition) — two independent, real `MilkdropMetalRenderer` instances, each with its own feedback-texture history, NS-EEL state, compiled shaders, and audio-onset smoothing, exactly matching upstream's dual-preset design. `draw(in:)` calls `renderToTexture` on both, then blends.
  - **`MilkdropSharedRenderResources` (same new file)**: switching presets can now happen every few seconds (auto-cycle) or faster (spacebar mashing), and each transition briefly needs *two* live renderer instances — so everything genuinely preset-*independent* (all ~15 static pipeline states, samplers, the noise texture catalog, fixed vertex/fragment functions, the mesh index buffer) was pulled out of `MilkdropMetalRenderer.init` into this new shared object, created once, passed into every renderer instance. Every reference to e.g. `device`/`solidPipeline` elsewhere in `MilkdropMetalRenderer.swift` is now a computed passthrough to `shared` with the exact same name — so none of the ~700 untouched draw lines needed to change. `MilkdropCustomTextureManager` (`customTextures`) was deliberately **kept per-instance**, not moved to the shared object, despite looking just as static — it caches an unkeyed, mutable "currently scanned root/random-slot-choices" (see MilkdropCustomTextureManager.swift), and sharing one across two simultaneously-live presets from *different* packs would let whichever renders second in a frame silently stomp the other's resolved textures. A real correctness bug caught by reading the manager's internals before assuming it was safe to share, not by trial and error.
  - **Transition trigger**: `ContentView.loadPresetAndTrack` now loads into a **fresh** `MilkdropVisualizerModel` instance rather than mutating the existing one in place — required so the outgoing preset's own live, still-evolving state (its feedback texture history, its per-frame script's carried-over custom variables) isn't destructively overwritten the instant the next preset loads; the renderer needs that state to keep rendering, live, for the transition's whole duration. `MilkdropMetalView.updateNSView` detects the new model is a different *instance* (`!==`) than last time and calls `MilkdropMetalCoordinator.updateModelIfNeeded`, which demotes the current `activeRenderer` to `outgoingRenderer` and creates a new one for the incoming preset — mirroring real projectM's own `StartPresetTransition` (including forcing an already-in-flight transition to immediate completion if a second load arrives before the first one finishes, rather than trying to juggle three simultaneous presets). A failed load's error is surfaced on the *existing* (still on-screen, unaffected) model, matching the old behavior of the alert appearing over whatever's still visible rather than over a discarded throwaway instance.
  - **Blend math, ported exactly, not approximated**: transition duration is real projectM's own default (`ProjectM.hpp`: `m_softCutDuration{3.0}`), not a guess. The blend curve is the exact cosine ease real projectM's own default/built-in transition shader uses (`TransitionShaderBuiltInSimpleBlendGlsl330.frag`'s `iProgressCosine`, derived in `PresetTransition.cpp`'s `Draw`: `(-cos(linearProgress * PI) + 1.0) * 0.5`) — computed once per frame on the CPU (cheap, avoids re-deriving per-pixel in MSL) and fed to a new `milkdrop_crossfade_fragment` (Shaders.metal) that samples both textures and `mix()`s them — real Milkdrop's simple/default blend is a literal `mix`, nothing fancier, so this needed no new pipeline complexity beyond one small fragment function.
  - **Explicit, documented simplifications vs. real Milkdrop/projectM**: (1) each renderer instance keeps its own independent audio-onset analyzer (`MilkdropBeatState`/`MilkdropSignalAnalyzer`) rather than the two presets sharing one computed `bass`/`mid`/`treb` — real projectM shares one `AudioData` struct across both `RenderFrame` calls; here, both analyzers see the same underlying `CoreAudioTapEngine` ring buffer (confirmed `snapshotWaveform()` is a non-consuming lock-protected read, safe to call from two independent instances the same frame) and converge to near-identical smoothed values, at the cost of a redundant FFT pass during the ~3s a transition is actually active. (2) the composite/warp shader `progress` uniform (a *different* concept from blend progress — real Milkdrop's per-preset "how far through this preset's own scheduled display duration" — see `TimeKeeper::PresetProgressA`) stays hardcoded at 0, unrelated to and unaffected by this work; Prism has no per-preset scheduled-duration concept at all (auto-cycle's fixed 20s timer isn't the same thing), so implementing that is a separate, not-yet-requested feature.
